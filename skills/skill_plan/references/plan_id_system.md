# 식별자 체계 & 레지스트리 규약 (plan_id_system)

> skill_plan v2 공통 규약. 모든 plan_* agent와 오케스트레이터가 준수한다.
> 목적: **요구사항·기능 등 식별자가 agent 간에 어긋나는 현상을 예방형으로 차단**한다.

## 1. ID 네임스페이스 (10종)

| ID | 의미 | 발번 문서 | 형식 |
|---|---|---|---|
| `FR-###` | 기능 요구사항 | 04 | 3자리 zero-pad |
| `NFR-###` | 비기능 요구사항 | 04 | 3자리 |
| `FN-{CAT}-##` | 기능 정의 | 05 | 카테고리코드 + 2자리 |
| `UT-###` | 사용자 유형 | 03 | 3자리 |
| `P-###` | 페르소나 | 03 | 3자리 |
| `BS-###` | 행동 시나리오 | 06 | 3자리 |
| `JM-###` | Journey Map | 06 | 3자리 |
| `SC-##` | 화면 | 07 | 2자리 |
| `ENT-###` | DB 엔티티 | 09 | 3자리 |

> 발번 문서만 해당 ID를 **생성**한다. 다른 문서는 **참조만** 한다.

## 2. 8 공통 카테고리 (FR ↔ FN 공유)

요구사항(FR)과 기능(FN)은 **반드시 동일한 카테고리 집합**을 공유한다. 이것이 FR↔FN 추적의 기반이다.

- 카테고리 코드셋은 `plan_requirement_analyzer`(04)가 **도메인에서 파생해 1회 확정**하고 freeze한다.
- 개수는 보통 6~10개. 코드는 3자 대문자(영문 약어).
- 예(컨텐츠 매니저): `QST 핵심객체 · CLS 분류 · SCH 검색 · BOK 핵심산출물 · FAV 개인화 · USR 사용자/권한 · MON 모니터링 · SEC 보안`.
- 04가 확정한 코드셋은 레지스트리에 실려 05·07·09 등 하위로 전달된다. **하위 agent는 새 카테고리를 만들지 않는다.**

```
04 requirements  ──[카테고리 코드셋 + FR 배정]──FREEZE──▶ registry
05 functions     ──FN-{CAT}-## : 동일 코드셋으로 FR을 전개(FR당 1개 이상 FN)──┘
```

## 3. FR ↔ FN 대응 규칙 (1:N + 전수 커버리지)

기능정의(FN)는 요구사항(FR)의 **구현 단위 분해**다. 대응 관계는 **1:1이 아니라 1:N**이며, 다음 불변식을 지킨다.

```
        ┌───────────────────────── 1 : N ──────────────────────┐
        FR-021 (교재 템플릿 등록·관리)
           ├─ FN-BOK-01  템플릿 파일 등록
           ├─ FN-BOK-02  자리표시자 문법 검증
           └─ FN-BOK-03  템플릿 버전 관리
```

- **1:N**: 한 FR이 여러 FN으로 전개될 수 있다(보통 그렇다).
- **전수 커버리지(불변식)**: **FN이 대응되지 않은 FR은 존재할 수 없다.** 모든 FR은 ≥1 FN으로 덮인다.
- **역방향**: 각 FN은 ≥1 FR로 소급된다(고아 FN 금지). 한 FN이 복수 FR을 동시에 충족할 수도 있다(N:M 허용).
- **카테고리 정합**: FN의 카테고리(`FN-{CAT}`)는 그것이 소급되는 FR의 카테고리와 일치한다.

> 즉 검증의 축은 "1:1 매핑"이 아니라 **"FR 전수 커버리지 + 카테고리 정합 + 고아 FN 0"**.

## 4. 레지스트리 운영 규칙 (예방형의 핵심)

**레지스트리 = 모든 발번 ID + 카테고리 코드셋의 단일 원천.** 오케스트레이터가 보유한다.

규칙:
1. **시드**: 04(requirement_analyzer)가 카테고리 코드셋 + FR/NFR을 확정 → 레지스트리 **시드**.
2. **불변 전달**: 오케스트레이터는 각 하위 agent에 레지스트리의 관련 슬라이스를 **불변 입력 `$$id_registry`**로 전달.
3. **참조 전용**: 어떤 agent도 상위 ID를 **재번호·재배정·재카테고리화하지 않는다**. 인용은 기존 ID 그대로.
4. **신규 발번만 허용**: 각 agent는 자기 네임스페이스(05=FN, 07=SC, 09=ENT…)의 **신규 ID만** 만든다.
5. **회수**: 오케스트레이터는 각 agent 산출에서 신규 ID를 회수해 레지스트리에 **append**(append-only, 삭제·재번호 없음).
6. **직렬 의존**: `req_analyzer(04) → function_specifier(05)`는 데이터 의존으로 **직렬화**한다. 05는 frozen FR을 입력으로만 받아 **모든 FR을 빠짐없이 FN으로 전개**하고, FR을 재번호하지 않는다.

```
$$id_registry 슬라이스 예 (function_specifier에 전달):
{
  categories: [QST, CLS, SCH, BOK, FAV, USR, MON, SEC],   # frozen
  FR: [ {id: FR-021, cat: BOK, title: 교재 템플릿 등록·관리}, ... ]   # frozen, 참조 전용
}
→ function_specifier는 위를 읽어 각 FR을 1개 이상 FN으로 전개.
  (예: FR-021 → FN-BOK-01/02/03). 누락된 FR이 없어야 한다.
```

## 5. 추적성 매트릭스

`05_functions §2`에 다음 매트릭스를 생성한다.

```
FN          ↔  FR        ↔  SC        ↔  ENT
FN-BOK-01      FR-021        SC-08         ENT-022
FN-BOK-02      FR-021        SC-08         ENT-023
FN-QST-01      FR-007        SC-03         ENT-009
...
```

- 한 FR이 여러 FN 행으로 나타날 수 있다(1:N).
- 각 FN/FR은 그것을 구현하는 화면(SC)·데이터(ENT)와 연결.
- **모든 FR이 매트릭스에 ≥1 행으로 등장**해야 한다(전수 커버리지).

---

## 6. 커버리지 규칙

- **05 functions**: 모든 FR이 ≥1 FN으로 전개되는지(FR 전수 커버리지), 고아 FN(소급 FR 없는 FN) 0인지 확인.
- **07 interfaces**: 모든 FR이 ≥1 SC에 매핑되는지(FR 커버리지). 고아 화면 점검.
- **09 database**: 모든 FR이 ≥1 ENT로 커버되는지 `§커버리지 확인`에 기록.
- **12 roadmap**: 모든 FR이 레이어/단계에 전수 매핑되는지.

## 7. 검증 게이트 체크리스트 (오케스트레이터, 최종 출력 직전)

산출 전 ID 무결성을 점검하고, 결손 시 **해당 agent만 재실행**한다.

```
[ ] FR 전수 커버리지 — 모든 FR이 ≥1 FN으로 전개됨 (FN 없는 FR = 0)   ★불변식
[ ] 고아 FN 0 — 모든 FN이 ≥1 FR로 소급됨
[ ] FR↔FN 카테고리 일치 (FN-{CAT} 의 CAT == 소급 FR 의 카테고리)
[ ] FR 재번호·누락 0 (05가 frozen FR을 변경하지 않음)
[ ] 고아 참조 0 — 문서가 인용한 모든 ID가 레지스트리에 존재
[ ] 중복 ID 0 (네임스페이스별 유일)
[ ] FR 커버리지 — 모든 FR이 ≥1 SC, ≥1 ENT
[ ] 추적성 매트릭스(FN↔FR↔SC↔ENT) — 모든 FR이 ≥1 행으로 등장
[ ] 카테고리 코드셋 단일 (04가 freeze한 집합 외 카테고리 없음)
```
